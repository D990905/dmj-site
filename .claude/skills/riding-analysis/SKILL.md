# 라이딩 세션 분석

옥대표 세션 파일을 **대시보드의 실제 엔진**(`riding-dashboard/js/`)으로 헤드리스 실행해
분석한다. 브라우저가 업로드 시 하는 것과 같은 경로 — 수치를 지어내지 않는다.

## 실행

```bash
node .claude/skills/riding-analysis/scripts/analyze.js <파일...> [--legs] [--json]
```

여러 파일을 주면 각각 따로 분석한다. **서로 다른 시간대 세션을 합치지 마라** —
융합은 같은 세션을 여러 기기로 잰 경우에만 쓴다(RaceBox 트랙 + Waterspeed 심박).

## 반드시 지킬 분석 규칙

이 규칙들은 전부 실측에서 틀렸다가 고친 것이다. 어기면 같은 실수가 반복된다.

### 1. 상위 티어는 성능 기준으로 잡는다 — 절대값이 아니라
힐·피치의 "상위 20%"를 값의 크기로 뽑으면 **"제일 많이 누웠을 때"** 가 되어 목표값이
못 된다. **VMG 기준으로 정렬**해 상위 구간의 자세를 봐야 "잘 갈 때 유지하던 값" 이 나온다.
실측 차이: 풍상 포트 힐이 절대값 기준 43.5° vs VMG 기준 **36.3°** — 7° 차이.

### 2. 풍상/풍하는 지속 레그만 쓴다
조건(|TWA|<70 등)만 맞으면 다 담으면 택 전환 직후 짧은 조각이 16~21% 섞인다.
**25초 이상 연속**을 레그로 보고, 통계 구간이 필요하면 레그 **안에서** 10초로 쪼갠다.
짧은 조각이 섞이면 "안정성이 VMG를 만든다" 같은 **가짜 상관**이 생긴다
(레그 안에서만 보면 힐 흔들림 차이가 정확히 0.0 이었다).

### 3. 그룹 간 비교와 그룹 내 관계를 구분한다 (Simpson 역설)
세션·택별로 힐 수준이 다르면, 그룹을 합쳐 본 상관은 조건 차이를 반영할 뿐이다.
반드시 **그룹 안에서** 다시 확인한다. 실제로 풍하 힐↔VMG 는 합치면 −0.27,
그룹 안에서는 힐↔속도 +0.18~+0.91 로 방향이 달랐다.

### 4. 동어반복 상관을 경계한다
힐은 `atan2(가로G, 수직G)` 로 계산한다. 그래서 **힐 ↔ 가로G 상관은 0.97** 이 나오는데
이건 검증이 아니라 같은 값의 두 표현이다. 마찬가지로 VMG = 속도×cos(풍각) 이므로
**VMG ↔ 풍각 상관 0.85~0.89** 도 부분적으로 정의상 당연하다. 이런 쌍은 근거로 쓰지 마라.
쓸 수 있는 것: 힐 **6.4° ≒ 가로힘 0.1g** 환산 (힐을 윙 압력계로 읽는 용도).

### 5. 자세 데이터는 조건이 맞을 때만 신뢰한다
- **RaceBox Bike Mode 금지** — GForceY 가 LeanAngle(오토바이 코너링 각)로 대체된다.
  직진 중 0 에 가까워 보드 힐을 못 잰다. 일반 모드 힐 ±30~44° vs 바이크 모드 ±7°.
- **센서가 보드에 눕혀 있어야 한다** — 가슴 착용 세션은 상체를 잰다. 엔진이 자동 거부한다.
- **0점 IQR** 을 함께 본다. 크면 절대값을 덜 믿는다.
- 좌우 차이는 실무상 **커봐야 3°**(옥대표). 그보다 크면 0점이나 습관을 의심한다.

### 6. 인과로 말하지 않는다
풍속 실측이 없어 "돌풍이 힐과 속도를 동시에 올린 것" 과 "힐이 속도를 만든 것" 을
가릴 수 없다. 관찰로 보고하고 한계를 함께 적는다.

## 도메인 지식 (옥대표 확인)

- **힐은 윙 압력에 대한 카운터밸런스다.** 윙 압력이 커야 속도가 나는데, 힐이 모자라면
  안정성이 떨어져 달릴 수 없다. 그래서 풍상(가로힘 0.55g)은 35°, 풍하(0.22g)는 13° 로
  하중에 비례한다.
- 실제 좌우 힐 차이는 **3° 전후**가 최대다.
- 피치는 풍상에서 노즈다운(−0.2~−1.2°), 풍하에서 노즈업(+0.3~+1.5°) 이 잘 나올 때 값.
